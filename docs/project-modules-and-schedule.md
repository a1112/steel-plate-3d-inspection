# 钢板三维检测项目模块与开发周期说明

## 一、项目概述

本项目面向钢板表面三维检测场景，核心目标是接入产线 3D 相机采集钢板表面深度数据，通过本地服务完成数据组织、缺陷记录、状态管理和接口输出，并在桌面端界面中完成实时监控、缺陷展示、报表查询、系统状态和采集配置管理。

项目整体按“采集层、服务层、界面层”三部分组织：

- 采集层：负责 3D 相机 SDK 接入、设备发现、连接控制、参数设置、深度图采集和采集状态回传。
- 服务层：负责钢板检测数据、缺陷数据、设备状态、历史记录和报表数据的统一接口。
- 界面层：负责操作员工作台、缺陷地图、报警分析、统计面板、报表导出、系统设置和采集管理。

当前代码结构已经按该方向拆分：

- `app/capture`：C++ 采集服务，面向 Capture 6.7.0.4 LVM/NVT 3D 相机 SDK。
- `app/service`：Rust 数据服务，提供检测业务数据接口。
- `app/client`：React + TypeScript + Tauri 桌面界面，承载主界面、报表、系统状态和采集管理。

## 二、总体架构

系统采用本地化部署架构，适合产线现场稳定运行。采集服务、业务服务和桌面界面部署在检测工位主机，3D 相机通过工业网络接入。

```text
3D 相机 / 工业网络
        |
        v
采集模块 app/capture
设备发现、连接、参数、深度图、状态
        |
        v
服务模块 app/service
钢板数据、缺陷数据、历史记录、统计报表、接口聚合
        |
        v
界面模块 app/client
实时检测、缺陷地图、报警分析、报表查询、系统管理
```

架构设计重点：

- 采集和界面解耦：相机 SDK、C++ 依赖和硬件环境集中在采集服务，界面通过 HTTP/Tauri 命令访问，降低界面复杂度。
- 服务和展示解耦：检测数据统一由服务模块输出，界面不直接拼装底层数据，便于后续接入真实算法、数据库和产线系统。
- 支持本地离线运行：关键链路在工位机本地闭环，减少网络波动对检测流程的影响。
- 支持渐进集成：前期可用模拟数据和本地接口完成界面、流程、报表验证，后期逐步替换为真实相机和真实检测算法。

## 三、项目模块划分

### 1. 采集模块

采集模块主要负责与 3D 相机和厂商 SDK 对接，是项目中对硬件、驱动和现场环境依赖最高的部分。

主要功能：

- 3D 相机 SDK 初始化和版本检测。
- 相机发现、IP 配置、连接和断开。
- 相机状态读取，包括连接状态、帧率、缓存、温度、丢脉冲、溢出等。
- 曝光、增益、触发、采集行数、输出路径等参数配置。
- 深度图或点云相关数据采集。
- 采集异常、SDK 错误码、连接错误和超时处理。
- 为界面和服务提供采集 API。

现有接口方向：

- `GET /health`：采集服务健康状态。
- `GET /api/cameras`：相机列表。
- `POST /api/camera/connect`：连接相机。
- `POST /api/camera/disconnect`：断开相机。
- `GET /api/camera/status`：读取相机状态。
- `GET /api/param`、`POST /api/param`：读取和设置相机参数。
- `POST /api/capture/depth-map`：触发深度图采集。

开发重点：

- SDK 调用稳定性。
- 工业网络和相机连接可靠性。
- 多相机同步和配置管理。
- 采集异常恢复机制。
- 与真实硬件的现场联调。

### 2. 服务模块

服务模块负责承接检测业务数据，是采集层、算法层和界面层之间的中间层。当前可先提供钢板、缺陷、状态和历史记录数据，后续可扩展为数据库存储、算法结果接入和产线系统对接。

主要功能：

- 钢板基础信息管理，包括板号、规格、钢种、检测时间等。
- 缺陷结果管理，包括缺陷类型、位置、尺寸、深度、严重等级、表面方向和预览图。
- 检测历史记录查询。
- 当前检测状态输出。
- 报表统计数据输出。
- 设备状态和运行状态整合。
- 为界面提供统一 HTTP API。

现有接口方向：

- `GET /api/inspection/snapshot`：返回当前检测快照，包括钢板、缺陷、状态、历史记录和统计信息。

后续扩展方向：

- 接入数据库，保存检测记录和缺陷明细。
- 接入算法模块，消费采集数据并生成缺陷结果。
- 接入 MES、L2 或厂内数据系统，获取板坯/钢板基础信息并回传检测结论。
- 增加权限、操作日志和审计记录。
- 增加批次查询、条件筛选和报表导出接口。

开发重点：

- 数据模型稳定性。
- 接口字段和界面展示的一致性。
- 检测记录可追溯。
- 高吞吐数据写入和查询性能。
- 与采集、算法、外部系统的边界定义。

### 3. 界面模块

界面模块是操作员和工程人员直接使用的桌面端工作台。当前采用 React + TypeScript + Tauri 实现，兼顾 Web 开发效率和桌面端部署能力。

主要功能：

- 实时检测主界面。
- 钢板俯视图、缺陷点位和上下表面展示。
- 缺陷列表、缺陷分类、严重等级筛选。
- 报警分析和统计面板。
- 历史记录查询。
- 在线报表、检测报表和 CSV 导出。
- 系统设置，包括检测阈值、显示规则、报表筛选等。
- 采集管理界面，包括相机状态、配置中心、日志记录和 API 管理。
- 桌面窗口控制和本地化运行。

界面开发重点：

- 产线现场可读性，适配大屏和操作台分辨率。
- 缺陷位置展示准确，支持快速定位和复核。
- 状态颜色、报警等级和操作反馈清晰。
- 长时间运行稳定，不因接口失败导致界面不可用。
- 报表、查询和导出流程符合现场使用习惯。

## 四、开发周期建议

如果以“可演示版本、可联调版本、可现场试运行版本、正式交付版本”逐步推进，建议整体周期按 12 到 16 周规划。若硬件、SDK、算法和现场网络条件提前准备充分，可压缩到 10 到 12 周；若需要深度算法训练、多相机同步和 MES 对接，周期应按 16 到 24 周评估。

### 阶段一：需求确认与架构设计，1 到 2 周

主要工作：

- 明确相机型号、数量、安装位置、视场范围和采样精度。
- 明确钢板规格范围、产线速度、检测节拍和缺陷类型。
- 明确数据流：采集数据、算法结果、业务数据、报表数据。
- 明确部署方式：单机、本地服务、数据库、外部系统接口。
- 确认界面信息架构和主要操作流程。

交付物：

- 项目架构说明。
- 模块边界和接口清单。
- 相机与现场网络配置清单。
- 开发计划和里程碑。

### 阶段二：采集模块开发与硬件联调，3 到 5 周

主要工作：

- 完成 SDK 初始化、设备发现、连接、断开和状态读取。
- 完成相机参数读写。
- 完成深度图采集接口。
- 完成单相机稳定性测试。
- 扩展多相机配置和状态管理。
- 增加错误码、日志和异常恢复。

交付物：

- 采集服务可执行程序。
- 采集 API 文档。
- 单相机和多相机联调记录。
- 采集异常处理说明。

主要风险：

- SDK 文档与实际行为不一致。
- 现场网络、网卡、IP 配置或驱动环境影响连接稳定性。
- 多相机同步、触发和数据带宽需要现场验证。

### 阶段三：服务模块开发，2 到 4 周

主要工作：

- 建立钢板、缺陷、记录、设备状态等核心数据模型。
- 完成检测快照接口。
- 增加历史记录、报表查询和统计接口。
- 根据现场流程补充操作日志和状态流转。
- 预留数据库和外部系统对接能力。

交付物：

- Rust 数据服务。
- 检测数据 API。
- 数据模型说明。
- 接口联调样例。

主要风险：

- 算法输出格式未稳定会影响服务数据模型。
- 报表字段和现场管理要求可能多次调整。
- 如果接入 MES/L2，外部接口周期可能成为关键路径。

### 阶段四：界面模块开发，3 到 5 周

主要工作：

- 完成检测主界面、钢板缺陷图和缺陷列表。
- 完成报警分析、统计面板、历史记录和报表页面。
- 完成系统设置、采集管理、日志和 API 管理页面。
- 完成接口失败、空数据、离线状态和长时间运行状态处理。
- 完成 Tauri 桌面打包和现场分辨率适配。

交付物：

- 桌面端应用。
- 操作员主流程界面。
- 报表和导出功能。
- 采集管理和系统状态界面。

主要风险：

- 现场大屏、工控机性能和分辨率差异影响界面适配。
- 缺陷定位图需要与真实钢板坐标、相机视场和算法坐标统一。
- 操作员流程需要通过现场使用反馈迭代。

### 阶段五：系统集成与试运行，2 到 4 周

主要工作：

- 采集、服务、界面联调。
- 接入真实相机和现场网络。
- 验证采集稳定性、数据完整性和界面刷新。
- 验证报表、历史记录和异常处理。
- 根据现场反馈修正操作流程和界面细节。

交付物：

- 现场试运行版本。
- 联调问题清单和关闭记录。
- 稳定性测试记录。
- 试运行报告。

### 阶段六：验收与交付，1 到 2 周

主要工作：

- 完成部署包、配置文件和运行说明。
- 完成现场验收测试。
- 完成操作培训。
- 固化版本和备份方案。
- 整理维护文档。

交付物：

- 正式交付版本。
- 部署说明。
- 操作手册。
- 接口文档。
- 验收报告。

## 五、周期影响因素

开发周期主要受以下因素影响：

- 硬件准备情况：相机、工控机、网卡、光源、触发信号和安装位置是否已确定。
- SDK 成熟度：SDK 是否稳定，文档是否完整，示例程序是否可运行。
- 算法范围：如果只做数据展示和结果接入，周期较短；如果需要新增缺陷识别算法、模型训练和精度验证，周期会明显增加。
- 多相机同步：相机数量越多，同步、带宽、缓存和异常恢复复杂度越高。
- 数据存储要求：是否需要长期存储全量深度图、点云、缺陷图片和报表数据。
- 外部系统对接：MES、L2、PLC、数据库和厂内权限系统都会影响联调周期。
- 现场验证条件：是否能持续占用产线环境进行测试，直接决定试运行周期。
- 验收标准：缺陷检出率、误报率、定位精度、响应时间和稳定运行时长需要提前明确。

## 六、建议里程碑

| 里程碑 | 时间 | 目标 |
| --- | --- | --- |
| M1 架构确认 | 第 1 到 2 周 | 完成需求、架构、接口和设备方案确认 |
| M2 采集打通 | 第 4 到 6 周 | 完成相机连接、参数读写和深度图采集 |
| M3 服务闭环 | 第 6 到 8 周 | 完成检测数据接口、历史记录和统计数据 |
| M4 界面可演示 | 第 8 到 10 周 | 完成主界面、缺陷展示、报表和系统状态 |
| M5 现场联调 | 第 10 到 14 周 | 完成真实硬件、真实网络和系统联调 |
| M6 验收交付 | 第 14 到 16 周 | 完成部署、培训、验收和文档交付 |

## 七、人员配置建议

建议基础配置：

- 采集/硬件工程师 1 人：负责相机 SDK、C++ 采集服务、现场网络和硬件联调。
- 后端工程师 1 人：负责 Rust 服务、数据模型、接口、存储和外部系统对接。
- 前端/桌面端工程师 1 人：负责 React/Tauri 界面、状态管理、报表和桌面打包。
- 算法工程师 1 人：如需要真实缺陷识别、点云处理或模型训练，则必须配置。
- 测试/现场实施 1 人：负责测试用例、现场部署、联调记录和验收支持。

若项目目标是先完成可演示和可联调版本，采集、服务、界面可由 2 到 3 名工程师并行推进；若进入现场试运行和正式验收，建议补齐测试和现场实施角色。

## 八、结论

本项目建议按“采集先打通、服务做中台、界面做闭环”的顺序推进。采集模块决定现场硬件可用性，服务模块决定数据和接口稳定性，界面模块决定操作员使用效率和验收观感。

在硬件和 SDK 条件明确的前提下，项目可按 12 到 16 周完成从架构确认到现场验收的完整交付；如果涉及复杂算法训练、多相机同步和外部系统深度对接，应按 16 到 24 周预留周期。
